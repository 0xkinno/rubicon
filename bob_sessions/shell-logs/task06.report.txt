### 8. What Happens When an Adapter Raises an Exception

In [`reconciler.py`](core/verifier/reconciler.py:126), the three `hash_state()` calls are wrapped in a `try/except`:

```python
try:
    pre_hash          = adapter.hash_state(pre)
    post_action_hash  = adapter.hash_state(post_action)
    post_rollback_hash = adapter.hash_state(post_rollback)
except Exception as exc:
    return DomainResult(
        domain=domain,
        result=DomainVerificationResult.NOT_OBSERVABLE,
        notes=f"Adapter error: {exc}",
    )
```

**Result:** Any unhandled exception from any adapter during any of the three `hash_state()` calls causes the entire domain to be tagged `NOT_OBSERVABLE`, with the exception message recorded in `notes`. This propagates upstream:
- The domain appears in the receipt's `limitations` list (via `_compute_limitations()`, line 186)
- If no `REMAINS_CHANGED` domain exists, the overall `ReceiptVerdict` rolls to `UNKNOWN` (line 182)

This is the correct fail-safe behaviour: an adapter crash means Rubicon **cannot make a claim** about that domain â€” it does not silently pass or fail the domain, and it does not halt the entire reconciliation. Other domains continue to be evaluated independently.
